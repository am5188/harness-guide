给 AI 装上手和脚

工具，
就是 AI 能按的「按钮」。

读文件、发邮件、搜网页——每一个都是 AI 可以调用的能力。 工具造得好，AI 如虎添翼；造得烂，它会被垃圾数据淹没。

先打个比方

手机 App 上的按钮，
就是人类的「工具」。

你想打车，点一下「叫车」——不用自己踩油门。 AI 也一样：它只会「想」，但点不了任何按钮。

所以我们给它造按钮：一个叫「读文件」，一个叫「发邮件」。 大脑决定按哪个，身体（Harness）负责真的去按。

好工具，
长这样。

判断标准很简单：这个工具对应 AI 真正要做的「一件事」吗？

🎯
少而精，一件事一个工具

别把每个 API 都包一遍。给「完成某任务」的复合工具，就像 App 里一个按钮干一件事。

🏷️
名字要让人一眼看懂

asana_projects_search 比 get_data 好——模型在几十个工具里才能在对的时机选对。

📋
参数写得明明白白

叫 user_id 不叫 user，必填项写清楚。像给新同事写操作说明，别让他猜。

⚡
返回结果要干净

只给有用的信息，别塞 UUID 和内部字段。失败了说清楚原因，别直接崩掉。

Claude Code 默认把工具返回限制在 25,000 token 以内——输出臃肿是真金白银的浪费。

好工具 vs 坏工具，
差在哪？

点下面标签，对比同一个场景下的两种做法。

打个比方：像给新同事一张任务清单——一步做完一件事，每个格子写得清清楚楚。

工具名
asana_projects_search
需要什么参数
{ "query": "项目名", "limit": 1-50 }
返回什么
只返回项目名和状态，默认 10 条一页
  • ·一件事一个工具：搜 Asana 项目，就叫 asana_projects_search
  • ·名字自带说明书：不会和 jira_search 搞混
  • ·参数精确：要 user_id 就写 user_id，别写含糊的 user
  • ·返回干净：不带 UUID 和内部字段，失败了说清楚原因

工具的通用插头

MCP，
就像 USB / Type-C。

Model Context Protocol（模型上下文协议）—— 一个开放标准，让不同软件的工具都能「插」到 AI 上。

以前每个 AI 客户端要单独对接每个工具。 有了 MCP，就像有了统一充电口——写一次，到处能用。

模型只「提议」，
Harness 才「执行」。

这是核心安全铁律：AI 不能直接动手，必须经过一道闸门。

模型提出
「我想读这个文件」
→
Harness 校验
参数对不对？你有权限吗？
→
执行并回填
真的去读，把结果塞回对话

每一步你都能拒绝——人在环中，不是摆设。

工具一多，
就塞不进脑子了。

几十个工具的定义全塞进上下文，又慢又贵又容易选错。 两招应对：按需加载，或者让 AI 写脚本去跑腿。

工具少的时候不用搞这些。等真的多了，再上。
